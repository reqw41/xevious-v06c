# Задание Codex: темп Xevious на Векторе

Работаешь в этом worktree (ветка `tempo-codex`). Не трогай `../xevious-v06c` и не пушь.

## Цель
Ускорить образ `build/xevious.rom` (ванильный Вектор-06Ц, i8080 3 МГц, кадр 59904 такта).
Сейчас одно обновление игры считается в среднем 2,25 кадра (стенд без гибели), у CPC — 2,03.
Каждый сэкономленный такт идёт в темп: опоздавшее обновление следующего кадра не ждёт.
Цель — как можно ближе к CPC; любой честный выигрыш принимается.

## Сборка и проверки (всё headless)
- Сборка: `node tools/vecbuild.js` (≈8 с; `--fast` — только ассемблер, если менялся лишь src/vec).
  Выводит занятость памяти; ошибки места — сообщения ассемблера/assert.
- Темп и сверка с CPC (главный критерий), три seed:
  `for s in 7 3 11; do node tools/vec/lockvec.js --seed $s --god --frames 8000 --rom build/xevious.rom --labels build/xevious.json | tail -1; done`
  Исходно: seed 7 — 2.28, seed 3 — 2.25, seed 11 — 2.27; «с расхождениями 0» обязательно.
  Без `--god` (обычная игра с гибелью) тоже должно быть 0 расхождений: `--seed 3 --frames 8000`.
- После изменений темпа: `for s in {1..12}; do node tools/vec/hangcheck.js build/xevious.rom build/xevious.json "$s" || exit 1; done` — все 12 seed должны дать `ok` (живые звук, ввод и гибель; 30000 кадров каждый).
- Панель: `for s in 5 7 11; do for mode in --god ''; do node tools/vec/hudcheck.js --seed "$s" --frames 30000 $mode || exit 1; done; done` — 0 ошибок, обе плоскости, гибель и переходы зон; эталон шрифта берётся из ROM (длинный прогон: --frames 120000).
- Профиль по процедурам (такты на обновление, со звуком): `node tools/vec/tempo_prof.js`.
- Счёт/ожидание по обновлениям: `node tools/vec/tempo_upd.js`.
- Если менялся код логики `src/i80/*.asm`: `node tools/i80build.js` и
  `node tools/cpc/oracle.js --i80 --area N` для N = 1..8, плюс `--god` — 0 расхождений.
- Экран: `lockvec ... --scr` сравнивает хэши экрана двух сборок по обновлениям
  (см. шапку tools/vec/lockvec.js). Изменение в выводе не должно менять картинку относительно исходной сборки
  (собери исходную в отдельную папку для сравнения).

## Шаг 4 (заменяет прежнюю переделку подписей панели): сдвиг панели копией через SP

Идея (от автора проекта). Полоса панели — 8 строк (7 строк знака + пустая) в столбцах 1..30, плоскости C и E
(и кораблики двухцветные). Сейчас `hud_draw` при каждом сдвиге прокрутки заново рисует все знаки из шрифта.
Вместо этого: при сдвиге прокрутки на d строк (vs_cur против hud_vs) **копировать уже нарисованную полосу из
видеопамяти** на новое место. Столбец в памяти Вектора — подряд идущие байты по строкам, так что для каждого
занятого столбца и плоскости это перенос 8 подряд идущих байт на d адресов (с учётом перекрытия и направления;
освободившиеся строки должны стать нулём — например, переносить 7+d байт, захватывая пустые строки).
Перенос — через стек: `ld sp,…` + `pop`/`push` (4 пары на 8 байт). На время, пока SP смотрит в видеопамять,
нужен `di` — но только на один столбец (короткий), затем `ei` и восстановление SP; не держи `di` на всю полосу.
Из шрифта рисовать только при изменении значений (hud_check NZ) и только изменившиеся знакоместа
(после копии на новом месте). Учти большие d и первый вывод (полная отрисовка, как сейчас).
Ожидание: панель ~10,9k → ~6k тактов на обновление.

совпадать на каждом обновлении), профиль `tempo_prof.js` (hud_draw до/после). Плюс проверь вручную дамп экрана

## Шаг 12 (после шага 11): сдвиг спрайта без полного стирания
Идея автора: у объекта, сдвинувшегося по вертикали (в координатах видеопамяти — сюда попадают и висящие на экране
воздушные, их сдвигает прокрутка), стирать не весь прямоугольник, а только строки, оставшиеся открытыми после сдвига.
Ловушка: спрайты рисуются по маске поверх фона, поэтому рисовать новый поверх старого нельзя — в прозрачных
точках останется старая картинка, а сохранённый фон новой позиции будет с остатками старого спрайта.
Рабочий вариант: для пересекающихся строк фон берётся из старого сохранённого фона (со сдвигом на dy),
для новых строк — из видеопамяти; итог (фон & маска | спрайт) пишется одним проходом, каждый байт один раз,
открывшиеся строки восстанавливаются из старого фона. Тогда спрайт вообще не бывает стёрт на экране.
Условия: тот же столбец/сдвиг по X (или обобщи), та же картинка или хотя бы ширина, нет пересечений с другими
спрайтами в этом/прошлом обновлении, иначе — как сейчас. Связь с шагом 11: то же «состояние спрайта между
обновлениями». Сначала замер: доля таких спрайтов и их вклад в мерцание (flicker.js); прошлый общий опыт
«стирать только задетое» (ветка flicker-spriso) замедлил на 17% и был остановлен — здесь темп не должен
ухудшиться заметно (≤1%), иначе остановись и опиши. Проверки — как в шаге 11. Патч 12-*.patch.
